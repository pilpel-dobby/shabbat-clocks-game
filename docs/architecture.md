# משחק שעוני שבת — סטאק טכנולוגי וארכיטקטורה

## מטרת המסמך
לתת כיוון טכנולוגי וארכיטקטוני ברור למימוש ה-MVP, בלי לקבע יותר מדי את המימוש הפנימי — כך שיהיה מספיק חופש פעולה לסוכן פיתוח, אבל עם גבולות נכונים.

## המלצת סטאק ל-MVP

### בחירה מועדפת
- **Frontend / App**: React + TypeScript
- **Build tool**: Vite
- **Styling**: CSS פשוט או CSS Modules
- **State management**: React state + custom hooks (בלי ספריית state כבדה בשלב ראשון)
- **Testing**:
  - Vitest ל-unit tests
  - Testing Library לרכיבי UI בסיסיים אם צריך
- **Runtime / deployment**: אפליקציית SPA סטטית בדפדפן

### למה זו ההמלצה
- TypeScript מתאים היטב למנוע סימולציה עם חוקים לוגיים ברורים
- React/Vite יאפשרו פיתוח מהיר, UI נוח, והרצה מקומית פשוטה
- אין כרגע צורך בשרת, בסיס נתונים, auth, או backend
- אפשר להפריד יפה בין מנוע המשחק לבין ה-UI

## מה לא צריך ב-MVP
- backend
- מסד נתונים
- משתמשים / התחברות
- שמירת התקדמות בענן
- מערכת חידות דינמית מלאה
- מנוע גרפי / canvas מורכב אלא אם יש צורך ממשי

## עקרון עליון ארכיטקטוני
יש להפריד בצורה ברורה בין:
1. **Game Engine** — הלוגיקה הדטרמיניסטית
2. **Puzzle Definitions** — נתוני החידות
3. **Application State / Orchestration** — ניהול מצב המשחק והאינטראקציה
4. **Presentation Layer** — רכיבי UI

המנוע צריך להיות כמה שיותר טהור ובלתי תלוי ב-React.

## חלוקת מודולים מומלצת

### 1. `core/` — מנוע הלוגיקה
מכיל פונקציות ומודלים טהורים בלבד.

#### אחריות
- לייצג שעון שבת
- לייצג שרשרת שעונים
- לחשב תנועת זמן
- לחשב מתי כל שעון מתקדם ומתי נעצר
- לחשב פלט סופי של חשמל לאורך טווח זמן
- להשוות בין פלט בפועל לבין יעד

#### מבנים אפשריים
- `ClockConfig`
- `ClockState`
- `ChainConfig`
- `SimulationConfig`
- `SimulationResult`
- `TimeSlotState`

#### פונקציות ליבה אפשריות
- `simulateChain(config, puzzleWindow)`
- `advanceClock(...)`
- `computeClockOutput(...)`
- `evaluateSolution(...)`
- `swapClocks(...)`

### 2. `puzzles/` — הגדרות חידות
מכיל נתוני חידות בלבד, לא לוגיקה UI.

#### כל חידה צריכה להגדיר
- מזהה
- שם
- תיאור
- טווח סימולציה (למשל 48 או 72 שעות)
- מספר שעונים
- מצב התחלה
- תבנית יעד
- פתרון אחד אפשרי לפחות
- מטא-דאטה עתידי (למשל קושי)

#### עיקרון חשוב
חידה היא **data-first**.
המנוע בודק אותה; ה-UI רק מציג אותה.

### 3. `features/game/` — שכבת המשחק
מחברת בין מנוע הלוגיקה ל-UI.

#### אחריות
- טעינת חידה
- ניהול מצב השעונים הנוכחי של השחקן
- ניהול debounce לסימולציה
- הפעלת סימולציה מחדש אחרי שינויים
- בדיקת הצלחה
- ניהול רמזים בעתיד

### 4. `components/` — רכיבי UI
רכיבים ויזואליים.

#### רכיבים סבירים ל-MVP
- `ClockEditor`
- `ClockChain`
- `ClockCard`
- `ToothStrip` או `ToothRing`
- `TimelineTarget`
- `TimelineCurrent`
- `PuzzleHeader`
- `HelpModal`
- `SimulationStatus`

## מבנה UI מומלץ ל-MVP

### דף בית / מסך ראשי
יכלול:
- כותרת
- כפתור התחלת משחק / מעבר לחידה
- כפתור עזרה / איך זה עובד

### מסך חידה
יכלול:
- תיאור החידה
- מספר השעונים שבשימוש
- אזור עריכת השעונים
- כפתורי החלפת סדר בין שעונים
- סרגל יעד
- סרגל מצב נוכחי
- חיווי הצלחה / אי הצלחה
- אולי כפתור reset
- אולי כפתור reveal hint בעתיד

## ייצוג זמן ב-v1

### רזולוציה
- כל צעד סימולציה = **שעה אחת**
- 24 צעדים למחזור שעון אחד

### המלצה פנימית
גם אם הייצוג הגרפי הוא שעות, כדאי לנסח API שמאפשר בעתיד רזולוציה כללית יותר.
למשל:
- `slotsPerCycle`
- `cycleLengthHours`
- `slotDuration`

כך יהיה קל יותר להרחיב לרבעי שעה בעתיד.

## עקרון סימולציה מומלץ

### דרישה מרכזית
הסימולציה חייבת להיות:
- דטרמיניסטית
- ניתנת לבדיקה
- מוסברת היטב בקוד

### מודל מומלץ
בכל tick:
1. קובעים מה מצב הקלט לכל שעון ברגע הנתון
2. קובעים מה מצב היציאה שלו לפי המיקום הנוכחי והאם יש קלט
3. מתעדים את מצב היציאה הסופי של השרשרת
4. מקדמים את מצב השעונים שמקבלים חשמל

### הערה חשובה
סדר הפעולות הזה צריך להיות מקובע ומתועד, כי הוא קריטי למקרי קצה של גבולות זמן.

אם במהלך המימוש AGY יגלה שמודל אחר אינטואיטיבי או נקי יותר, אפשר לשנות — אבל חייבים:
- לבחור כלל עקבי אחד
- לתעד אותו
- לבדוק אותו בטסטים

## טסטים מומלצים

### חובה ב-MVP
Unit tests למנוע.

#### תרחישים חשובים
- שעון בודד דולק/כבוי לפי תבנית
- שעון בודד מתקדם רק כשיש קלט
- שעון בודד קופא כשאין קלט
- שני שעונים בשרשרת
- שבירת מחזוריות על פני יותר מ-24 שעות
- wrap-around במעבר חצות
- השוואה נכונה בין יעד לפלט בפועל
- החלפת סדר בין שעונים משנה תוצאה כמצופה

### nice to have
- snapshot או בדיקות פשוטות לייצוג timeline
- בדיקות אינטגרציה בסיסיות למסך החידה

## נתונים ופורמטים

### יעד חידה
כדאי לייצג את תבנית היעד כמערך בוליאני/בינארי באורך מספר ה-slots בטווח החידה.

לדוגמה:
- `true` = דולק
- `false` = כבוי

אותו פורמט בדיוק ישמש גם לפלט הסימולציה. כך ההשוואה תהיה פשוטה.

### מצב שעון
כדאי לייצג כל שעון עם:
- מזהה
- צבע
- מערך שיניים
- מיקום נוכחי
- פרמטרים עתידיים (כמו slotsPerCycle)

## שיקולי UX / ביצועים
- debounce של בערך 500–1000ms לאחר שינויי משתמש
- חישוב סימולציה מחדש על כל שינוי משמעותי, אבל לא על כל mousemove בודד
- מאחר שה-MVP יכלול מעט שעונים ורזולוציה של שעה, אין עומס חריג צפוי
- לכן עדיף קוד פשוט ונקי על פני אופטימיזציית יתר

## גמישות להרחבה עתידית
הארכיטקטורה צריכה לאפשר בהמשך:
- שעונים עם מספר שיניים שונה
- רזולוציה של רבע שעה
- מחזוריות שאינה 24 שעות
- מפצלים / branching
- חידות מרובות
- רמזים אוטומטיים
- דירוג קושי
- generator של חידות

### לכן חשוב להימנע כרגע מ:
- hard-code קשיח מדי ל-24 שעות בתוך כל שכבה
- ערבוב בין UI ללוגיקה
- חידה שמקודדת ישירות בתוך רכיב React בלי שכבת data

## החלטות פתוחות שמותר להשאיר ל-AGY
כדי לתת חופש פעולה סביר, מותר ל-AGY להכריע בכפוף לעקרונות לעיל על:
- שמות תיקיות ומודולים מדויקים
- האם להשתמש ב-CSS Modules או CSS רגיל
- איך בדיוק לייצג ויזואלית את השעון (חוגה עגולה, רצועת שיניים, או גרסת MVP פשוטה יותר)
- האם ציר הזמן יוצג כ-bars, cells, או heat-strip
- האם להתחיל עם SVG, divs, או UI פשוט אחר

## החלטות שלא כדאי להשאיר עמומות מדי
הסוכן צריך לשמור על אלו:
- מנוע נפרד מה-UI
- Unit tests למנוע
- שעה אחת לשן ב-v1
- סדר שעונים ניתן לשינוי
- ציר יעד מול ציר מצב נוכחי

## המלצת עבודה ל-AGY בשלב הבא
השלב הבא מול AGY צריך להיות בערך:
1. להקים שלד פרויקט וובי

3. להוסיף puzzle definition אחת
4. לבנות UI מינימלי עובד
5. לחבר סימולציה + צירי זמן
